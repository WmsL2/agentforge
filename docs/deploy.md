# Single-host production deployment

The supported production path is GNU Make plus docker-compose.prod.yml. This
contract is implemented statically; real deployment validation is NOT RUN.
Atomic 3 does not authorize operating any existing infrastructure.

## Prerequisites and private inputs

Use a POSIX shell with GNU Make, grep, awk, tr and coreutils. Docker Compose must
be >= 2.33.1 (gw_priority support); Make checks its version before deployment
changes. Windows development tests use Git sh and a fake Docker executable;
this is not Windows Docker/Desktop deployment certification. No WSL is required
or started by the tests.

Choose a new project identity matching agentforge-prod-[a-z0-9][a-z0-9-]{0,39}.
Choose RELEASE_ID matching [a-zA-Z0-9][a-zA-Z0-9_.-]{0,63}; dev/latest (any case)
are rejected. Identity inputs are mandatory on every operation, including logs/down.
Do not operate concurrently: one maintainer serializes build/deploy/update/cleanup.

Prepare a private backend/.env.prod from the public .env.prod.example manually.
Alternatively select an explicit .env.prod.<id> variant; development .env, public
examples, missing files and file symlinks are rejected. No existing private file
is read or generated by this implementation task. Git/Docker ignore rules protect
these private variants. Use forward-slash paths from a POSIX shell. Make makes the
selected path absolute (cygpath when present), uses it for both --env-file and
backend role env_file, and always passes --project-name. Shell interpolation
wins over file values; shared mappings keep infra/backend credentials consistent.
Do not export unintended overrides or print rendered config/Settings/URLs.

Supply Atomic 2 required secure settings plus explicit PYTHON_IMAGE, UV_IMAGE,
BUN_IMAGE, POSTGRES_IMAGE and REDIS_IMAGE. Select verified immutable registry
refs (repository@sha256:actual-digest) for reproducibility. No digest is invented
or automatically resolved here. Preserve Python 3.12 Debian-slim conventions,
Bun Debian useradd support, PostgreSQL 16/pgvector 0.8.7 and Redis 7 compatibility.
Lockfiles are frozen, but this is not proof of bit-for-bit reproducible builds.

## Artifact preparation, startup and updates

The following are operator commands, NOT executed as part of Atomic 3. Use your
approved project/release/file instead of the illustrative identifiers:

```bash
make docker-prod-build PROD_PROJECT=agentforge-prod-example RELEASE_ID=r1 PROD_ENV_FILE=backend/.env.prod
make prod PROD_PROJECT=agentforge-prod-example RELEASE_ID=r1 PROD_ENV_FILE=backend/.env.prod
make prod-logs PROD_PROJECT=agentforge-prod-example RELEASE_ID=r1 PROD_ENV_FILE=backend/.env.prod
make prod-down PROD_PROJECT=agentforge-prod-example RELEASE_ID=r1 PROD_ENV_FILE=backend/.env.prod
```

Build-only explicitly pulls the configured DB/Redis artifacts, builds backend
once through app and builds frontend. All five backend roles share
agentforge/<project>-backend:<release>; frontend uses
agentforge/<project>-frontend:<release>. They never pull application images
implicitly. Use a fresh release ID per artifact; do not rebuild/re-tag a release
in use. Retain image IDs/build inputs and verify provenance externally.

prod validates identities/file/tool version and quiet Compose config, obtains
image refs and verifies all selected images locally before affecting containers.
It refuses an already-running migration, stops only this project's five business
roles, removes only its stopped migrate container (no stop/volume option), then
runs dependency-gated up --detach --no-build --pull never. It never rebuilds or
pulls implicitly during startup. A fresh migrate runs alembic upgrade head after
DB TCP readiness. Every business role requires service_completed_successfully;
frontend additionally depends on API start. DB/Redis health is not schema success.

Before stopping any business role, prod runs a temporary configuration-only
preflight through the selected migrate image/config:
`run --rm --no-deps --pull never -T migrate python -c "from app.core.config import settings; print('CONFIGURATION_VALID')"`.
It overrides Alembic, has no media mount, starts no dependencies and imports only
Atomic 2 Settings/load_settings. Invalid config exits before stop/rm/up. Compose
run can create project networks even with no-deps; authorization/cleanup must cover
them. Only the temporary preflight container is automatically removed. This proves
neither database/Redis/Provider connectivity nor complete readiness. See
[Compose run semantics](https://docs.docker.com/reference/cli/docker/compose/run/).

The project is a repository component and release is the tag, so the valid pairs
(agentforge-prod-a, b-r1) and (agentforge-prod-a-b, r1) have distinct repositories
instead of colliding through hyphen concatenation. This remains local image
selection, with no registry publication.

Use the same build/select then prod sequence for an update with a fresh release
ID. Removing the old migrate container prevents old successful state satisfying
another release's gate. Every command failure propagates; no fallback restarts
old business roles after migration failure. Investigate and obtain an approved
recovery decision; do not run destructive schema downgrade as routine recovery.
Bare docker start/restart or ad hoc Compose commands can bypass this supported
lifecycle and are not governed by its gate. Startup exit success is not a claim
of readiness or completed full-stack verification.

docker-prod, docker-prod-down and docker-prod-logs are aliases to the same
scoped paths. docker-prod-build never starts services. Normal down does not
remove volumes, images or unrelated projects. No automatic orphan/volume cleanup.
Keep the original release inputs available for scoped stop/log operations.

## Network, storage and exposure

DB, Redis, Beat, Flower, migrate and frontend use only <project>_backend-internal.
API/Worker additionally use <project>_provider-egress with gateway priority 1.
This provides an explicit default egress path, not a hostname firewall or a
complete security policy. Actual deterministic Provider DNS/reachability remains
NOT RUN; commercial requests require separate authorization.

API/Frontend/Flower bind loopback by default. API_BIND_HOST/API_HOST_PORT,
FRONTEND_BIND_HOST/FRONTEND_HOST_PORT and FLOWER_BIND_HOST/FLOWER_HOST_PORT
make bindings explicit; DB/Redis have no published ports. NEXT_PUBLIC_API_URL,
NEXT_PUBLIC_WS_URL and NEXT_PUBLIC_SITE_URL are public browser-reachable build
inputs, not container DNS or private credentials. Changing them requires a new
frontend artifact. BACKEND_URL remains http://app:8000 internally. COOKIE_SECURE
stays true by default: plain HTTP is not a supported workaround for production
authentication. TLS/proxy/public exposure is Atomic 6; no nginx config is supplied.

Project-scoped postgres_data, redis_data and media_data volumes preserve existing
mount destinations. API/Worker share the same private-media volume and backend
non-root user identity; fresh volume ownership must be verified at runtime.
Existing volumes under older project identities are NOT silently adopted,
renamed/copied/deleted. Any data migration requires separate authorization.
Redis volume presence is not a zero-data-loss or backup guarantee. Backup/restore
and private-media consistency drills remain Atomic 5. Indexing consumes DB parsed
content; shared originals do not imply a file reread for indexing.

## Verification and recovery boundaries

Infrastructure checks: PostgreSQL TCP pg_isready excludes the temporary local
socket server; authenticated Redis CLI must succeed and return PONG without
printing credentials. Migration proves schema upgrade success separately.
Inherited API HTTP probes are disabled for migrate/Worker/Beat/Flower until A4
implements role-specific checks; API/frontend/full health semantics remain A4.

Basic /api/v1/health returns status healthy plus max_upload_size_mb; it is not
worker/provider readiness. Validate login, async runs/indexing, RBAC, private
files, images/migrations/network and persistence in the separately authorized
[isolated runtime plan](v0.13/atomic3-deployment-infrastructure.md). No runtime
PASS follows from static YAML, fake-Docker Make tests, backend image CI or
independent browser HTTP fixtures. Keep database/media backups paired; recovery
requires an approved compatible schema/artifact/restore plan.

Old Fly/Railway/Render/Vercel template quickstarts are not authoritative for this
contract and have been removed: URL env injection and frontend static-site
assumptions did not establish compatibility with current computed Settings and
standalone Next runtime. No cloud resource provisioning is included.
