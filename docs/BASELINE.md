# AgentForge Foundation Baseline

## 1. Purpose

AgentForge is an **Enterprise Agent Workflow Platform**.

Its purpose is to provide an engineering platform for building, composing,
executing, controlling, and observing enterprise Agent workflows.

AgentForge is not intended to be:

- a ChatGPT wrapper;
- a generic AI chat application;
- a standalone RAG knowledge base;
- a LangGraph demo;
- a generic SaaS starter.

The long-term AgentForge architecture is centered around:

- Workflow Domain Model;
- Workflow Validation and Compilation;
- Workflow Execution Engine;
- Workflow Versioning;
- AgentRunner Protocol;
- Native Agent Runtime;
- LangGraph Agent Adapter;
- Tool Registry and Tool Executor;
- MCP integration;
- Tool Policy;
- Persistent Checkpoint;
- Pause and Resume;
- Human-in-the-loop approval;
- Workflow Run / Run Step / Trace;
- Agent observability;
- Workspace and RBAC;
- background workflow execution.

The guiding ownership rule is:

> The foundation provides common web engineering infrastructure.
> AgentForge implements the Agent Platform Core.

The objective of v0.1 is not to implement the Workflow Engine.

The objective is to produce a clean, stable, owned engineering baseline on
top of which the AgentForge Platform Core can be implemented.

v0.1 includes:

- GitHub Actions CI;

## 7. Template Takeover Audit

Template functionality is classified using four decisions:

- KEEP — directly useful foundation capability;
- REMOVE — unrelated to the AgentForge platform goal;
- REWRITE — useful location or concept, but current implementation represents
  the wrong product;
- DEFER — potentially reusable later, but must not define the current
  architecture.

### KEEP

Keep the following foundation areas:

- authentication;
- users;
- sessions;
- database/session infrastructure;
- SQLAlchemy;
- Alembic;
- Repository/Service structure;
- health checks;
- core configuration;
- logging;
- middleware;
- Redis;
- rate limiting;
- Celery application infrastructure;
- Docker;
- CI;
- test infrastructure;
- Next.js application shell;
- authentication UI;
- profile UI;
- reusable UI primitives.

### REMOVE

The following generated product functionality does not belong to the
AgentForge product direction and should be removed after dependency/reference
analysis:

- generic contact/sales backend;
- message rating product feature;
- user slash-command product feature;
- generic SaaS pricing;
- generic marketing testimonials;
- fake customer/company logos;
- generic blog;
- generic community pages;
- generic help center;
- template changelog pages;
- unsupported billing claims;
- unsupported integration claims;
- unsupported SSO claims;
- unsupported RBAC claims;
- unsupported RAG/data-source claims.

Removal must include all corresponding:

- routes;
- schemas;
- services;
- repositories;
- models where safe;
- frontend pages;
- frontend components;
- frontend constants;
- tests;
- dependencies;
- documentation references.

Files must not be deleted independently when other modules still import them.

### REWRITE

The following areas are conceptually useful but currently represent the
wrong product:

- root landing page;
- dashboard;
- navigation/sidebar;
- README;
- architecture documentation;
- configuration documentation;
- deployment documentation;
- generated product copy;
- project metadata;

They should be rewritten around the AgentForge platform rather than around a
generic AI SaaS/chat/RAG product.

Any feature shown in the UI or README must be clearly classified as either:

- implemented;
- current foundation;
- planned.

Planned AgentForge capabilities must not be presented as already available.

### DEFER

The following generated AI capabilities are retained temporarily as reference
implementations:

- basic LangGraph assistant;
- current agent service;
- basic chat/conversation execution path;
- OpenAI integration;
- current WebSocket/chat transport;
- file upload/storage infrastructure.

The LangGraph implementation is not the AgentForge Workflow Engine.

The current chat stack is not the final AgentForge Agent Runtime.

These modules may be isolated, simplified, adapted, or removed when the
AgentRunner and Knowledge architectures are implemented in their respective
versions.

## 8. Cleanup Principles

Template cleanup follows these rules.

### 8.1 Preserve the foundation before deleting product features

Each cleanup batch must maintain:

- application importability;
- database migration validity;
- backend tests;
- frontend type checking;
- frontend tests;
- application startup.

### 8.2 Delete by feature slice

A product feature should be removed vertically.

For example:

`message ratings`

should be removed across:

`route -> schema -> service -> repository -> model -> frontend -> tests`

rather than deleting random files one by one.

### 8.3 Do not prematurely implement later versions

v0.1 cleanup must not silently become v0.2 development.

In particular, do not add:

- Workflow models;
- Workflow nodes;
- DAG execution;
- Workflow editor;
- AgentRunner;
- Tool Registry;
- MCP;
- Checkpoint;
- HITL.

### 8.4 Do not preserve template code only because it already exists

Existing code is retained only when it supports the AgentForge roadmap.

Code volume is not a project goal.

### 8.5 Do not remove reusable infrastructure only because v0.1 does not use it

Redis and Celery are examples.

They are retained because later AgentForge versions require durable/background
Workflow execution.

### 8.6 Keep LangGraph behind an architectural boundary

LangGraph may later implement an AgentRunner adapter.

It must not become the AgentForge Workflow Engine.

AgentForge must remain able to explain where platform orchestration ends and
third-party Agent framework execution begins.

## 9. Known Foundation Issues and Cleanup Debt

The following issues are known at the v0.1 Foundation stage.

### Generator / Environment

- generated backend `.env` behavior did not match generator output messaging;
- `.env.example` mixes local and production Redis password examples;
- generated Alembic history referenced an omitted MCP migration;
- a no-op `0026_create_mcp_connections` migration was added to repair migration
  continuity.

### Backend

- Pydantic deprecation warnings remain;
- Python project requirement is 3.12 while Ruff/ty configuration still targets
  Python 3.11;
- temporary Celery smoke task remains;
- template chat-specific models and services remain pending cleanup.

### Frontend

- ESLint warnings remain;
- Vite CJS API deprecation warning remains;
- generated marketing/product pages remain;
- current dashboard remains chat/RAG-oriented;
- runtime configuration deprecation requires later cleanup;
- some generated frontend package versions should be normalized;
- blog/MDX dependencies should be removed if blog functionality is removed.

### Docker / Development

- Windows `make dev` has shell compatibility issues;
- local Windows Celery requires the solo execution pool;
- Docker Compose variants contain some runtime differences that should be
  documented or normalized.

### CI

- Foundation CI is green;
- backend coverage currently uses a practical v0.1 baseline;
- frontend coverage currently applies to a scoped Foundation module set;
- full AI/chat E2E is intentionally not a blocking Foundation CI gate;
- deterministic Auth + Home Chromium E2E is the blocking Foundation E2E gate;
- PostgreSQL healthcheck logging can be cleaned up to avoid default `root`
  connection noise;
- GitHub-hosted runners currently report Node runtime deprecation warnings for
  some third-party Actions.

## 12. Ownership Statement

A concise explanation of AgentForge ownership is:

> AgentForge uses a mature FastAPI + Next.js full-stack template as its web
> engineering foundation. Authentication, database integration, Redis,
> background-task infrastructure, Docker, and basic application structure are
> inherited foundation capabilities. The Workflow Engine, Agent Runtime
> abstractions, Tool/MCP platform, durable Checkpoint/HITL execution,
> observability, and enterprise resource model are designed and implemented
> specifically for AgentForge.

This boundary should remain visible in the codebase, documentation, Git history,
and project interviews.
